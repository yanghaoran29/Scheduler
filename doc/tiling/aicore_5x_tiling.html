这个数是怎么算的

本页是设计/分析文档的整理页，不是脚本扫仓自动生成的报表。分块数字分三类，不要混读。

列 / 数字类型含义怎么得到
当前逻辑分块 / 当前 BlockDim 改参前 main 默认构图 读源码 tiling 常量手算。例如 Qwen out_proj：N_SPLITS_OUT × K_SPLITS_OUT = 10 × 5 = 50；Attention：ATTN_SPMD_BLOCKS=24；CSA 默认 T=B×S=4×2=8。
目标逻辑分块 / 目标 BlockDim 面向 120 AIC 的方案 设计取值（改哪个 tile 常量、为何选 N 不选 K），不是上板测量值。
验证占用 / span / golden 24 AIC 设备上的实测 来自 deps.json + 四级泳道；不能反推「目标分块」表。120 AIC 目标机性能仍需另采。

术语

  • BlockDim：一次任务调用启动的并行 Block 数；普通 pl.at 的 BlockDim 为 1。
  • 逻辑分块总数：该算子全部工作块，可跨多次 pl.at / pl.spmd，不等于同时在跑。
  • 切分 Batch：是 = block 索引含 Batch/Token；否 = 每 block 处理完整 Batch tile；间接 = 表达式含行组但本次不切该维。

常用公式例

Qwen out_proj（基线）:  N_SPLITS_OUT × K_SPLITS_OUT = 10 × 5 = 50
Qwen out_proj（目标）:  20 × 5 = 100
Qwen Attention 工作项: active_batch × NUM_KV_HEADS = 16 × 8 = 128
Qwen gate/up:          17 × 5 = 85
CSA qk_pv（目标）:     T × SPARSE_BLOCKS = 8 × 5 = 40
CSA score（目标）:     T × REDUCE_NSPLIT = 8 × 10 = 80
CSA proj_a「8×16」:    8 次调用 × 每次 BlockDim 16（≠ 一次 BlockDim 128）

文档 A：5× AICore 并行切分方案

源文件：工作区根目录 AICORE_5X_TILING_PLAN.md（中文原文）。

1. 目标与范围

本方案面向 AICore 数量由 24 增加到 120 的机器，模型规格保持代码仓默认值，不调整隐藏维度、Head 数、Batch 上限或序列长度。

  • Qwen3：models/qwen3_14b/decode_fwd.py::_decode_layer
  • DeepSeek CSA：models/deepseek_v4_flash_mtp/decode_csa.py
  • 基线：当前 main，提交 c3f0dea274f55d9648920f17c968e8564ae9fcdc

文中的“BlockDim”指一次任务调用启动的并行 Block 数；普通 pl.at 任务的 BlockDim 为 1。表中的“逻辑分块总数”用于描述同一算子的所有工作块，不代表这些块一定属于同一次任务调用或一定能同时运行。

Batch 标记含义：

  • 是：Block 索引显式包含 Batch/Token 维度，Batch 大小会影响有效工作项数量或并行度。
  • 否：每个 Block 都处理完整的 Batch tile，新增并行度来自 N、K、Head 等非 Batch 维度。
  • 间接：表达式包含行组，但本次修改不切分该维度；默认规格下通常只有一个行组。

2.2 Q/K/V 保持 50/10/10 的原因

Q、K、V 的输出计算量约为 5:1:1。当前任务数也是 50:10:10，所以三类任务的单 Block 工作量接近一致。

如果只把 Q 改成 100：

  • Q 的单 Block 工作量减半，但 K/V 仍是原来的长任务；
  • 100 + 10 + 10 = 120 只是在数量上填满 120 核，并不代表工作量均衡；
  • QKV 汇合点可能继续等待 K/V 长尾；
  • 更多 Q Block 还可能占用 K/V 的调度窗口。

因此第一版保持 Q/K/V = 50/10/10。只有目标机泳道图证明 q_proj 是独立关键路径、且 K/V 被完全隐藏时，才单独试验 100/10/10。如果整个 QKV 阶段都需要加速，应按相同粒度同步切分，例如 100/20/20，但该方案共有 140 个 Block，会在 120 核上形成第二波，不能作为默认首选。

2.3 Attention：24 → 120

修改位置：models/qwen3_14b/paged_attention_pypto.py。

ATTN_SPMD_BLOCKS: 24 -> 120

默认单个 Batch window 最多有：

active_batch × NUM_KV_HEADS = 16 × 8 = 128 个逻辑工作项

BlockDim 120 时，前 8 个 lane 各执行两个工作项，其余 lane 各执行一个工作项。这里明确切分了 Batch × KV Head；实际 Batch 小于 15 时，逻辑工作项少于 120，部分 AICore 会空闲。是否提高 Batch，应根据目标服务负载决定，不能为了填核直接修改模型默认 Batch。

需要同步检查依赖于 ATTN_SPMD_BLOCKS 的 transfer/workspace 尺寸，特别是 TRANSFER_ROWS，不能只替换 BlockDim 常量。

2.4 Out Projection：50 → 100

推荐沿 N 维加倍，不增加 Split-K：

N_SPLITS_OUT: 10 -> 20
K_SPLITS_OUT: 5  -> 5
OUT_TN:       512 -> 256
OUT_TK:       1024（保持）
总分块:       10×5=50 -> 20×5=100

选择 N 维而不是 K 维的原因：

  • Split-K 保持 5，避免把 atomic-add 扇入从 5 增加到 10；
  • 减少 atomic 竞争和浮点累加顺序变化风险；
  • [BATCH_PAD, OUT_TN] 累加器从 512 列降到 256 列，片上空间压力更低；
  • 每个 Block 仍处理完整 BATCH_PAD，没有切分 Batch。

当前实现把 50 个逻辑块组织为 26 个普通任务和一个 BlockDim 24 的直接 SPMD 任务，这是调度优先级设计，不是矩阵形状要求。目标版本不应简单保留 76 个普通任务 + BlockDim 24，否则 Attention 完成后的第一波仍只有 24 个直接块。建议分两步实施：

  1. 先完成 20 × 5 的 100 分块，验证数值和 tile 资源；
  2. 再在 120 核目标分支中把 100 个块组织为直接 SPMD，或根据泳道图保留少量延迟块。

第二步会改变调度关系，必须通过 deps.json 和四级芯片泳道图确认没有挤压更关键的早发任务。

2.5 Gate/Up/Down 保持 85

Gate 和 Up 当前为 17 × 5 = 85 个逻辑块；Down 也是 85 个逻辑块。它们已经能覆盖 120 核的大部分并行能力，继续翻倍会显著增加任务启动、权重读取和 Split-K/atomic 开销。第一版保持不变，只有泳道图显示单块时间过长且存在持续空核时再调。

3.1 Batch 维度说明

  • qr_hadamard_matmul：Block 索引为 T × HeadTile，包含 Batch/Token。
  • score：Block 索引为 T × REDUCE_NSPLIT，包含 Batch/Token 和 cache reduction split。
  • qk_pv：40 个逻辑工作项来自 T × SPARSE_BLOCKS = 8 × 5，明确包含 Batch/Token。
  • merge_norm：Block 索引为 T × (H / MERGE_H_TILE)，明确包含 Batch/Token。
  • kv_score_proj：BlockDim 公式含 BS_PAD / MM_B_TILE 行组，但默认 T=8 被装入一个 16 行物理 tile；本次 16 → 64 只通过缩小输出 N tile 实现，不新增 Batch 切分。
  • 其余 Matmul 任务都在每个 Block 内处理完整的默认 Token/Batch 行，新增并行度来自 N 或 Split-K。

3.2 merge_norm 32 → 64 的实现约束

不能直接把 decode_sparse_attn_csa.py 中共享的 H_TILE 从 16 改成 8。实际编译已经证明该直接修改会使 qk_pv 生成 [8, 512] FP32 Acc tile，而 PTO cube 物理行必须是 16 的整数倍；同时 8 个 FP32 标量只有 32 字节，多个 QK Block 写相邻区域时存在 64 字节 cache-line 共享风险。

推荐把生产者和消费者 tile 解耦：

QK_STORE_H_TILE = 16   # qk_pv 物理存储和 cache-line 粒度保持不变
MERGE_H_TILE    = 8    # merge_norm 每个 Block 处理 8 个 Head

qk_pv 继续按 16 Head 写满 64 字节的 mi/li 行组；两个 merge_norm Block 分别消费同一个 16-Head 组的前半和后半。这样可以得到 BlockDim 64，同时不引入 8 行 cube tile 和跨 Block cache-line 写冲突。该调整需要重写 merge_norm 的 producer-group/sub-group 索引，属于中等修改量。

3.3 其他主要风险

  • qproj_matmul 128：120 核上会形成 120 + 8 的尾波；N tile 从 512 降到 256 后需要检查 GM/L1 搬运效率。
  • qr_proj_matmul 64：Split-K 从 2 增至 8，单 Block 更短，但 atomic-add 扇入扩大 4 倍。
  • kv_proj_matmul 32：Split-K 从 4 增至 8，存在相同的 atomic 竞争风险。
  • idx_qr_proj_* 32：MM_N_TILE 必须和 Q_OUT_TILE 一起降到 256，否则每个任务会覆盖相邻任务的输出范围。
  • qr_hadamard_matmul 32：M tile 从 64 降到 16，Hadamard 权重的重复读取比例上升。
  • score 80：每个 reduction lane 的有效 cache 工作量依赖序列长度，短序列可能出现大量短任务。
  • qk_pv 40：已经等于默认的 40 个有效工作项；继续增加 BlockDim 不会产生更多有效并行工作。
  • kv_score_proj 64：输出 tile 从 64 降到 16，单次写回很小，需要关注搬运效率和任务启动开销。

4. 实施与验证顺序

建议按以下顺序落地，避免一次修改过多后无法定位回退点：

  1. Qwen3 保持 Q/K/V 和 MLP 不变，只调整 Attention BlockDim。
  2. Qwen3 Out Projection 改为 20 × 5，先验证矩阵 tile，再调整直接/延迟任务比例。
  3. DeepSeek 先调整各 Matmul、Indexer、Score、QK 和 Compressor 参数。
  4. DeepSeek 单独实现 producer/store 与 merge_norm Head tile 解耦。
  5. 每一步都使用仓库默认规格做编译和数值验证。
  6. 在 120 核目标机采集 deps.json 与四级芯片泳道图，检查实际调度波次和关键路径。

验收指标：

  • 默认规格数值测试通过；
  • 无 tile shape、L0C/L1/UB 超限或 cache-line 共享诊断；
  • deps.json 中任务依赖没有新增不必要的串行边；
  • 目标任务在 120 核泳道图中确实提高并发，而不是只增加短任务或尾波；
  • 端到端关键路径缩短，atomic 竞争和任务启动开销没有抵消收益；
  • 对所有标记为“切分 Batch”的任务，分别检查真实服务 Batch 和默认 Batch，决定是否需要单独的 Batch 配置档。

1. 结论

本方案后续修改以 zhusy54/pypto-lib 的 aicore-5x-tiling 分支

该分支已经完成第一版 120 AICore tiling：Qwen Attention 已设为120，Out Projection

已设为100，DeepSeek CSA 的目标 tiling 也已落入源码。后续修改必须保留

ATTN_SPMD_BLOCKS = 120 和 BATCH_PAD = 16。不能通过把 Batch 从16改为24来制造

192个 Attention 工作项，因为那会改变 benchmark 工作量，而不是只修改 tiling。

私有工作镜像为 yanghaoran29/pypto-lib-aicore-5x-tiling，本地克隆目录为

pypto-lib-aicore-5x-tiling-private。其 origin 指向私有镜像，upstream 指向

zhusy54/pypto-lib，不会与 hw-native-sys/pypto-lib 的现有工作树和远端混淆。

当前改造在保留全部逻辑 blocks 的前提下按数学依赖聚合任务：

  1. Out Projection 的100个 blocks 分成10个 spmd(10)；每组覆盖2个相邻 N tile

和5路 Split-K。

5. seq_len、Batch 和其他任务变长因素

5.1 Qwen3

只有 paged attention 的主计算随每个请求的 seq_lens[b] 明显增长：

page_count  = ceil(seq_len / 128)
stack_count = ceil(seq_len / 512)

每个 (batch, kv_head) 工作项执行 stack_count + PRE_LAUNCH 个 tick，QK/PV 总工作量近似与 seq_len 成正比。混合长短请求时，静态 grid-stride 映射会产生 lane 长尾；把 BlockDim 提高到 120 并不能消除这种长度不均衡。

其他因素：

  • active_batch 改变 attention 的逻辑工作项数 8B，但 Q/K/V、out 和 MLP 都仍计算完整的 BATCH_PAD=16 行，因此它们的单 block 工作量不随真实 batch 下降。
  • 公共 batch 大于 16 时，decode_fwd 按 16 行 window 串行执行，端到端时间约随 ceil(batch/16) 增长。
  • MAX_SEQ 主要决定 KV pool、RoPE 表和 block table 的容量；真正决定本次 attention 循环长度的是运行时 seq_lens[b]。

  • QKV 汇合点仍可能等 K/V 长尾；
  • 额外 Q block 可能挤占 K/V 的调度窗口。

第一目标因此保持 50/10/10。仅当目标机泳道证明 Q 独立关键且 K/V 被完全隐藏时，再试 100/10/10。三者同比例扩到 100/20/20 共 140 blocks，在 120 核上必然第二波，不作默认。

2.3 Attention：24 → 120

修改位置：models/qwen3_14b/paged_attention_pypto.py。

ATTN_SPMD_BLOCKS: 24 -> 120

默认单个 Batch window 最多有：

active_batch × NUM_KV_HEADS = 16 × 8 = 128 个逻辑工作项

BlockDim 120 时，前 8 个 lane 各执行两项，其余各一项。这显式切分 Batch × KV Head。active Batch 小于 15 时逻辑项不足 120，部分 AICore 会空闲。更大 Batch 应由服务负载决定，不能仅为填核。

ATTN_SPMD_BLOCKS 同时决定 transfer / workspace（含 TRANSFER_ROWS），只改 launch 维度不够。

Phase 0 现为独立 BlockDim-16 任务，每 block 用 2 条 AIV，共 32 lanes。BlockDim-120 的 Attention 依赖 Phase-0 TaskId。该生产者-消费者边替代 mixed-kernel 的 syncall，保证 Q/K/V GM 交接顺序，且不要求 120 个 Attention block 同时驻留。Attention 无跨 block 同步、不请求 sync_start，可增量调度。

2.5 Out Projection：50 → 100

增大 N 切分，保持 Split-K：

N_SPLITS_OUT: 10 -> 20
K_SPLITS_OUT: 5  -> 5
OUT_TN:       512 -> 256
OUT_TK:       1024（不变）
合计:         10×5=50 -> 20×5=100

选择理由：

  • atomic-add 扇入保持 5，而非增到 10；
  • 限制 atomic 竞争与累加顺序精度风险；
  • [BATCH_PAD, OUT_TN] 累加器从 512 列降到 256 列；
  • 不切 Batch；每 block 仍处理完整 BATCH_PAD。

基线把 50 个逻辑块组织为 26 个普通任务 + 一个直接 BlockDim-24 SPMD。第一版 120 核曾改为一次 100-block SPMD。当前分组为十个 BlockDim-10 任务：每任务覆盖两个相邻 256 列 N tile 与全部五路 Split-K。相邻两个 Out TaskId 正好产出一个 1024 列 residual_rms_cast slice，保留 slice 粒度释放，且不退回「一 block 一任务」。

2.6 按输出 tile 聚合 Gate / Up

Gate 与 Up 各保留 17 × 5 = 85 逻辑块。对 17 个 intermediate N tile，各有一个 Gate spmd(5) 与一个 Up spmd(5) 计算五路 Split-K partial。Gate 与 Up 互不依赖。对应 SiLU tile 只等三个 TaskId：共享 RMS reduction、其 Gate SPMD、其 Up SPMD；不等待另外 16 个输出 tile。

Down 保留 85 逻辑块。每个 Down Split-K block 仍只依赖产生其 intermediate K slice 的那一个 SiLU，保留 17 路 Gate/Up/SiLU→Down 流水。

3.1 Batch 维细节

  • qr_hadamard_matmul：索引为 Token × HeadTile。
  • score：Token × cache reduction split。
  • qk_pv：40 项 = T × SPARSE_BLOCKS = 8 × 5。
  • merge_norm：T × (H / MERGE_H_TILE)。
  • kv_score_proj：BlockDim 含 BS_PAD / MM_B_TILE 行组表达式，但默认 8 token 装入一个 16 行物理 tile；16→64 仅靠缩小输出 N tile。
  • 其余 matmul 每 block 处理完整默认 Token/Batch 行；新并行来自 N 或 Split-K。

3.2 Merge Norm：32 → 64

不能把共享 Head tile 直接从 16 改成 8：会生成非法 [8, 512] FP32 cube 累加器（物理 cube 行须为 16 的倍数）；8 个 FP32 仅 32 字节，相邻 QK block 可能共享 64 字节 cache line。

因此解耦生产/消费 tile：

QK_STORE_H_TILE = 16  # QK/PV 物理存储与 cache-line 粒度
MERGE_H_TILE    = 8   # 每个 merge_norm block 消费的 Head 数

QK/PV 继续写 16 Heads 并填满 64 字节 mi/li 组；两个 merge_norm block 分别消费每个 16-Head 组的下半与上半。得到 BlockDim 64，且不引入 8 行 cube tile 或跨 block cache-line 写。

3.3 主要风险

目标机有 120 个物理 AIC。某任务的 BlockDim 是其自身最大并行度，不是全图利用率：独立就绪任务可共享机器。因此需要目标机 deps.json 与四级泳道，才能区分「孤立的低 BlockDim」与「真实空闲区间」。

qproj_matmul=128：规则 tile + 八 block 尾波

输出宽 64 heads × 512 = 32768。256 列 tile 下，128 个 block 写互不重叠的 [16, 256] INT32 区、无 atomic，故数值安全。但在 120 AIC 上，下游要等第二波 8 个 block 完成后才能看到 TaskId 完成。旧 64-block 用 512 列 tile、每 block 约两倍工作。理想线性缩放下，一波 64 与两半波 128 孤立计算时间相近，新布局还付尾调度成本。32768 / 120 不是整 Cube tile，故无法均匀 120 路切分。64 vs 128 是经验关键路径选择，不能单从 BlockDim 推出。

qr_proj_matmul=64 与 kv_proj_matmul=32：Split-K 扇入

qr_proj_matmul 有八个 128 列 N 组与八路 K split；同组八个 partial atomic-add 到同一 [16, 128] FP32 区。Split-K 2→8 使 K slice 缩短 4 倍，同时 atomic 写流量与扇入 ×4。64 blocks 可同波驻留 120 AIC，每区八个写者可能同时活跃；累加顺序也可能改 FP32 低位。

kv_proj_matmul 有四个 128 列 N 组与八路 K；扇入 4→8，BlockDim 仅 16→32。它不在主 Q 路径上，可与其它就绪分支重叠，故 26.7% 孤立占用不等于整机空闲。仅当目标泳道显示并发阶段更短且 atomic 尾不更大时，才保留 Split-K 8。

idx_qr_proj_*=32：输出所有权是硬不变量

Indexer 输出宽 64 × 128 = 8192。Q_OUT_TILE=256 给出 32 个互斥任务区；MM_N_TILE=256 使每任务恰好一次匹配 Cube 写。若 MM_N_TILE > Q_OUT_TILE，相邻任务重叠。当前取相等；一般安全条件：

Q_OUT_TILE % MM_N_TILE == 0
MM_N_TILE <= Q_OUT_TILE
(IDX_N_HEADS * IDX_HEAD_DIM) % Q_OUT_TILE == 0

Matmul 与 dequant 必须继续使用同一 Q_OUT_TILE 划分。这是正确性要求，不是性能旋钮。

qr_hadamard_matmul=32：更多并行行，权重重复读

行数 T × IDX_N_HEADS = 8 × 64 = 512。M tile 64→16 使 BlockDim 8→32，每 block 行工作量降为 1/4。每 block 仍读完整 [128, 128] BF16 Hadamard（32 KiB）。块级权重读合计约从 256 KiB 增到 1 MiB。cache 复用可减 HBM 流量，但去不掉重复 GM→L1 与 Cube setup。用 AIC busy、MTE2 busy 与任务墙钟对比 M=64/32/16。

score=80：有效 lane 依赖序列长度

80 blocks = T=8 × REDUCE_NSPLIT=10。一个 reduction tile 为 BLOCK_SIZE / COMPRESS_RATIO = 128 / 4 = 32 压缩 token，故每 token 有效 lane：

min(10, ceil(visible_compressed_length / 32))

原始可见长度 ≤128 时约 8/80 有用；约 512 时 32 有用；约 1024 时 64 有用；约 1156 以上才可能 80 全有用。零迭代 lane 不改正值但仍有调度成本。产品决策需分短/中/长上下文测量；短序列桶或宜 REDUCE_NSPLIT=2 或 4。

qk_pv=40：当前分解只有 40 项

默认形状恰好 T × SPARSE_BLOCKS = 8 × 5 = 40 独立项。只增 NUM_QK_CORES 会产生零迭代 lane。按 Head 再切可暴露更多并行，但当前项把一块 sparse KV 收进 L1 并在 Head 组间复用；Head 切分会重复 gather 并需改结果布局或 merge。除非测过该算法改动，否则保持 40。

kv_score_proj=64：最窄 Cube 列 tile

主 ratio-4 compressor：一个 pad 后的 16 行组投影到 1024 列。N tile 64→16 使 BlockDim 16→64。权重区仍互斥、总字节不变，但公共 [16, 4096] 输入被 64 个 block 消费（原 16）。无 cache 复用时输入流量约 2 MiB→8 MiB。N=16 也是最小 Cube 列 tile，固定 setup/transfer 更难摊销。这是一次 SPMD launch 而非 64 次 kernel，但每 block 仍付自己的 setup。目标机对比 N=64/32/16。

目标机验收标准
  1. 把 Indexer 输出 tile 关系当作编译期正确性不变量。
  2. 测量 qproj 在 64 与 128 blocks；检查八 block 尾是否拉长图关键路径。
  3. 扫 QR Split-K 2/4/8 与 KV Split-K 4/8，同时看墙钟与数值漂移。
  4. 扫 Hadamard M 64/32/16 与 compressor N 64/32/16。
  5. 在代表性服务序列长度上测 score，而非只测最长夹具。
  6. 除非重设计 Head 分解，保持 qk_pv=40。
  7. 只以端到端目标机墙钟接受 tiling；BlockDim 或核忙碌改善只是解释性指标，不是加速本身。
